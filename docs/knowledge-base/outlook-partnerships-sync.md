# Outlook → Notion Partner Pipeline sync

Scans configured Outlook mailboxes for partnership mentions and, after human review, writes them into the Notion Partner Pipeline database that `haven-va` already manages (`src/notion.ts`'s `createPartner`/`RECORD_DB_CONFIGS.partners`).

**This is not part of the live bot.** It doesn't touch `src/bot/`, `src/crons/`, or the Telegram message pipeline documented in [`bot-architecture.md`](bot-architecture.md). It's a set of local scripts plus a Claude Code skill (`.claude/skills/sync-partnerships/SKILL.md`) that a founder runs on demand, always with a human-review step before any Notion write — there is no unattended/auto-write path.

## This doc now covers a manual tool AND a live bot cron

**As of 2026-09-21, there are two separate Outlook→Notion partnership paths, not one:**

- **This doc's original subject** — `scan-outlook-partnerships.mjs` + `apply-outlook-findings.mjs` + the `sync-partnerships` skill — is a manual, human-reviewed, on-demand audit/backfill tool. Still exactly as described below: read-only scan → human review → explicit apply. Partner Pipeline only (never writes Influencer Pipeline). Still keyword-based (`OUTLOOK_PARTNERSHIP_KEYWORDS`), not LLM-classified.
- **`src/crons/sync-partnerships.ts`** — a live bot cron (`CLAUDE.md`'s crons table, 08:14 Mon), fully automated, no human review gate. Writes BOTH Partner and Influencer Pipeline. Uses an LLM classifier (`src/prompts/partnership-email-intent.md`) instead of keywords for anything that isn't a known contact — full automation was judged unsafe on keyword matching alone, given this doc's own confirmed false-positive history (SaaS/vendor noise, the "91thelabel" keyword-miss case below). Same relationship `scripts/dry-run-instagram-leads.mjs` has to the live `leads-instagram-scan.ts` cron: the manual flow stays available for ad-hoc audits, but it is no longer the live path.

They share `src/lib/outlook-contact-matching.ts` (the known-contact email/domain lookup logic — `normalize`/`domainOf`/`guessExternalParty`/`buildContactLookups`/`matchKnownContact`, promoted out of `scan-outlook-partnerships.mjs` this same day so both tools use one implementation) and `src/lib/entity-enrichment.ts` (the Sobre/Deal/Log + structured-property fill, also shared with `leads-instagram-scan.ts` and the live assistant's manual `create_entity` chat tool). Everything else below in this doc that describes `scan-outlook-partnerships.mjs`/`apply-outlook-findings.mjs` specifically (keyword list, `$filter` design, the manual checkpoint file, the skill) still applies only to the manual tool, not the cron.

## Why two separate scripts

`scripts/scan-outlook-partnerships.mjs` (read-only) and `scripts/apply-outlook-findings.mjs` (the only Notion-write path) are deliberately separate. This makes "never write without review" a structural property of the code, not just a prompt instruction — there's no code path from "scan Outlook" to "create a Notion page" that skips a human looking at a report in between.

## Setup

### 1. Azure app registration (must be done outside Claude Code)

1. portal.azure.com → **Microsoft Entra ID → App registrations → New registration**. Single-tenant, Web redirect URI `http://localhost:3000` (a placeholder — never an actually-running server, we just read `?code=` off the URL pasted back, same pattern as `GOOGLE_REDIRECT_URI`).
2. Copy the **Application (client) ID** and **Directory (tenant) ID** from Overview.
3. **Certificates & secrets → New client secret** — copy the value immediately, it's shown once.
4. **API permissions → Add a permission → Microsoft Graph → Delegated permissions**: `Mail.Read`, `Mail.Read.Shared`, `offline_access`.
5. **Grant admin consent** for the tenant (may need a Global/Application Administrator).
6. **Separately confirm with the M365 admin**: the account that will authenticate has **Full Access** Exchange delegate permission on every non-`me` mailbox to be scanned (`Add-MailboxPermission -Identity "shared@domain" -User "you@domain" -AccessRights FullAccess`, or Exchange Admin Center → Mailbox delegation). **This is the single most likely setup failure** — without it, Graph calls to `/users/{mailbox}/messages` 403 even with `Mail.Read.Shared` consented, and the error looks like a bug rather than a missing permission grant.

### 2. Env vars

See `.env.example`'s `# Outlook / Microsoft Graph` block: `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `MICROSOFT_TENANT_ID`, `MICROSOFT_REDIRECT_URI`, `MICROSOFT_REFRESH_TOKEN_MADALENA` (prod-only override, see gotcha below), `OUTLOOK_MAILBOXES` (comma-separated, `me` implicit), `OUTLOOK_PARTNERSHIP_KEYWORDS` (optional extra keywords).

### 3. Authenticate once

```bash
npm run build
node --env-file=.env.local scripts/outlook-auth.mjs
```

Writes `outlook-tokens.json` under `DATA_DIR` (mirrors `google-tokens.json`'s role for Google Calendar).

## Running it

Use the `sync-partnerships` skill (`.claude/skills/sync-partnerships/SKILL.md`) — it walks through checkpointed scanning, review, and apply. For a one-off manual run, see the `Usage:` header comments in `scripts/scan-outlook-partnerships.mjs` and `scripts/apply-outlook-findings.mjs` directly.

## Design decisions worth knowing

- **`$filter`, not Graph `$search`.** Graph's `$search` on messages is relevance-ranked and has known quirks combining with pagination/filters (requires `ConsistencyLevel: eventual`). Instead: pull messages in a date range via the cheap, deterministic, indexed `$filter=receivedDateTime ge …`, then keyword-match `subject`+`bodyPreview` client-side (accent-folded, case-insensitive). Simpler to reason about, trivially extensible via `OUTLOOK_PARTNERSHIP_KEYWORDS`.
- **JSON scan report, not CSV or a Notion staging page.** CSV loses the structured metadata (matched keywords, matched-partner info) the apply step needs. A Notion staging page would mean writing to Notion during the supposedly read-only phase, and adds a second schema to maintain.
- **Guessed partner name falls back to the recipient when the Haven itself sent the message.** A reply from `partners@thehavenpilates.pt`/`hello@`/`geral@` would otherwise guess "Partners"/"The Haven"/"Geral" as the partner name — useless, since those are the Haven's own addresses. `scan-outlook-partnerships.mjs` calls `outlook.getMyEmail()` once per run plus the domains of `OUTLOOK_MAILBOXES` to build an "own domains" set; when `from`'s domain is in that set, it uses the first external `to` recipient instead. Confirmed against real data during initial setup (2026-09-14) — see the "Last touched" entry below.
- **Two-tier detection: exact identity by email/domain, fuzzy title matching only as a fallback for brand-new senders.** Every Partner Pipeline page has an `Email` property; `notion.getAllPartnerContacts()` reads all of them once per scan and `scan-outlook-partnerships.mjs`'s `buildContactLookups()`/`matchKnownContact()` check every message's sender (and, when the Haven itself sent it, its recipients) against that table *before* keyword matching runs. A hit is a `known_contact` finding — identity is certain, no title-guessing needed, and critically it's independent of keywords entirely: it catches ongoing correspondence with a known partner that never uses a partnership-sounding word (a message about scheduling a call, or a refund, that keyword-matching alone would never surface). Verified against real production mail 2026-09-15 — two genuine zero-keyword matches ("Re: Fizemos um refund" → Creche Botãozinho, "Uma ideia para a comunicação..." → NX Dynamics), neither of which would have been found any other way. Domain-level matching (treating "anyone @company.com" as the same partner) is opt-in per domain — excluded for public/free providers (`PUBLIC_EMAIL_DOMAINS` in the script; real partner contacts routinely use personal gmail/icloud addresses, so domain-matching those would misattribute unrelated senders) and for any domain shared by more than one existing partner page (ambiguous, falls back to keyword+fuzzy rather than guessing). For findings that don't match a known contact, dedup is still approximate — fuzzy title search (`findPageInDb`/`findRecordByTitle`) against a guessed name, same as before. A "possible_match" (or "known_contact") is always a suggestion for the human reviewer, never auto-applied.
- **A domain match only proves "same organization," never "same initiative" — `matchBasis` exists precisely to not conflate the two.** Confirmed wrong for real, the day after this shipped: `76256@novasbe.pt` (a student address) domain-matched to the existing "Nova SBE (Well-Being)" partner for a pitch about a completely unrelated program ("Nova Thirst Project"). A large organization — a university is the clearest case, but any company with multiple departments/programs has the same risk — can run many distinct things under one domain. So every `known_contact` finding carries `matchBasis: "exact_email" | "domain"`: `exact_email` (the literal same address emailing again) is certain and skips the reviewer's dedup double-check same as before; `domain` keeps that check — the sync-partnerships skill's Step 4 treats a domain match as a strong hint of *organization*, never a resolved identity of *which partnership record it belongs to*.
- **The Haven's own domains are excluded from the contact lookup entirely, not just from domain-matching.** Found for real during verification: a partner's `Email` property had been mistakenly set to a founder's own `@thehavenpilates.pt` address during an earlier apply run ("GetYourGuide" — since fixed, cleared to empty), which without this exclusion caused every internal Haven email to false-match it (34 of 46 messages in one test scan). A real partner contact is never on the Haven's own domain, so `buildContactLookups()` drops any stored contact email on one of `ownDomains` before it ever reaches either lookup map — a blanket safeguard against this class of bad data recurring, not a one-off patch for that single row.
- **`Notas` is never touched by this pipeline** (create or update) — `buildPartnerProperties()` in `apply-outlook-findings.mjs` sets `Último contacto` unconditionally and `Status`/`Próximo passo`/`Email` only when the reviewer's decision provides them, but never `Notas`; anything not fitting "Sobre o parceiro"/"Deal e proposta" goes in the page body instead. (This bullet previously and incorrectly claimed `update` never touches `Status` either — it does, whenever `decision.status` is set, same as `create`.)
- **Page-body updates (`"📓 Log"` and the rest of `bodySections`) are selective, reviewer-judged, not automatic.** See the `sync-partnerships` skill's Step 4 for the exact "when does a finding get a Log line" judgment call — only findings/merged-groups with genuinely new information get one, dated to the email's own `receivedDate`, not every finding in a thread. **When several raw findings get merged into one decision (the existing "pick the most recent as anchor" convention), the Log needs ONE LINE PER DISTINCT REAL EVENT in that thread, not one summary line for just the anchor's final state** — got this wrong the first time it shipped (see "Last touched" below), losing entire negotiation arcs. Same `"📓 Log"` toggle section the live Telegram assistant writes to when a founder reports a meeting/call directly (`src/prompts/assistant.md`'s "Atualização/reunião com parceiro" section) — one combined chronological history regardless of source; that path is inherently single-event per message, so this multi-line concern only applies to the email-scan side.
- **No new npm dependencies.** Plain `fetch` against Graph REST + the OAuth v2.0 token endpoint (`src/lib/outlook.ts`) — the actual surface needed is ~4 endpoints, not worth `@azure/msal-node` + `@microsoft/microsoft-graph-client` on a codebase with zero prior Microsoft dependencies.
- **Confirmed emails get forwarded + archived out of whichever mailbox they came from, but only after review, not on a mere keyword match.** `apply-outlook-findings.mjs` forwards the original email to `OUTLOOK_PARTNERSHIP_FORWARD_TO` (e.g. `partners@thehavenpilates.pt`) and archives it from `finding.mailbox`, for every mailbox this pipeline scans (personal or shared — `me`, a colleague's, `geral@`, `hello@`, anything in `OUTLOOK_MAILBOXES`), once the founder's decision actually applies (`create`/`update`, not `skip`). Originally scoped to only the shared inboxes (mirroring tidy-mailboxes.ts's invoice forward+archive), broadened 2026-09-14 at the founder's request to cover every configured mailbox — no separate mailbox allowlist needed since a finding only ever exists for a mailbox this sync already scans. The read-only/write-only script split (see above) still holds: a false-positive keyword match in the scan report never touches the mailbox, because nothing happens until a human's decision reaches the apply step.

## Gotchas

- **Microsoft rotates refresh tokens on every use — unlike Google's, which stay valid indefinitely.** `outlook.ts`'s `getAccessToken()` therefore treats `MICROSOFT_REFRESH_TOKEN_MADALENA` as a one-time bootstrap only: once the first refresh succeeds, the rotated token is written to `outlook-tokens.json` and used from then on. If you ever delete the token file, the env var works again as a fresh bootstrap — but don't rely on the env var staying valid indefinitely the way `GOOGLE_REFRESH_TOKEN_MADALENA` does.
- **`updateRecord()`'s rich_text writes overwrite, they don't append** — see [`notion-api-gotchas.md`](notion-api-gotchas.md). `Notas` is deliberately left untouched by this pipeline (not auto-filled on create or update) precisely to avoid this trap; only page-body sections accumulate content, via `appendToPageSection`, which does append.
- **A 403 on one specific mailbox and not others** almost always means that mailbox is missing the Exchange Full Access delegate grant — it's not a code bug, see setup step 6.
- **Flagged, not fixed (founder's call, 2026-09-21): `tidy-mailboxes.ts` can hide a partnership/influencer email from BOTH this scan and `sync-partnerships.ts` before either ever sees it.** `tidy-mailboxes.ts` (daily, unattended, `OUTLOOK_TIDY_MAILBOXES`) auto-archives any thread its own classifier judges resolved, with no human review. `outlook.ts`'s `searchMailboxMessages()` — used by both `scan-outlook-partnerships.mjs` and `sync-partnerships.ts` — deliberately excludes the Archive folder ("already handled by this pipeline or tidy-mailboxes", see that function's own docstring). If a mailbox is in both `OUTLOOK_TIDY_MAILBOXES` and this pipeline's mailbox list, tidy-mailboxes can archive a genuine partner/influencer thread before either scan ever runs against it — silently gone, no trace, no error. This is the exact same risk that keeps `leads-email-scan.ts` disabled (see `CLAUDE.md`'s crons table). Not fixed here — the founder explicitly chose "flag the risk, don't fix it now" when this was raised during `sync-partnerships.ts`'s design (2026-09-21) — revisit if a real miss is ever reported. A one-line pointer to this same paragraph also lives in [`tidy-mailboxes.md`](tidy-mailboxes.md).
- **The scan's dedup check runs against the *guessed* name, before a human corrects it during review** — so `apply-outlook-findings.mjs` re-checks `findPageInDb("partners", nome)` against the FINAL name right before every `create`, not just trusting the scan-time bucket. Without this, correcting a guessed name (e.g. a contact's personal name → the actual company name) during review can silently turn an existing partner into a duplicate. This happened for real on 2026-09-14: the scan guessed "Ana Luisa Silva" for a Track & Field email (matched no existing row), a human corrected it to "Track & Field" during review, and the apply script created a second "Track & Field" page alongside an existing one it never re-checked against. Fixed by adding the re-check; the duplicate was merged back into the original page by hand.

## Checkpoint state

`data/outlook-sync-state.json` (gitignored, same `DATA_DIR`-relative convention as the token file): `{ "<mailbox>": { "lastSyncedISO": "..." } }`. The `sync-partnerships` skill reads/advances this so re-running doesn't re-surface already-reviewed emails; a 1-day overlap buffer is applied on the `--since` used for each scan to tolerate any consistency lag near the boundary.
